# Mastiff: gavana's auth layer

Status: v1 design, decided by Ben 2026-10-12 (axum; app-owned users table
generated by scaffolding; Postgres, SQLite, MySQL). Nothing is built yet.
Review notes from the same day are at the bottom.

## Goals for v1

- Email + password sign up, log in, log out.
- Server-side sessions with secure cookies.
- Extractors so handlers can ask for the current user by type.
- Password reset by emailed one-time token.
- CSRF protection for form posts.
- Login throttling.
- Storage written in prepared `.sql` files, so Mastiff dogfoods the data layer.

Not in v1, designed so they fit later: API tokens, OAuth/social login,
TOTP/WebAuthn MFA, email verification, roles/authorization policies.

## Crate shape

    src/
      lib.rs         re-exports, Mastiff config builder
      password.rs    PasswordManager (argon2id), hardened per below
      session.rs     token generation, cookie handling, expiry
      extract.rs     CurrentUser<U>, MaybeUser<U>, Auth<U>, MastiffLayer
      csrf.rs
      throttle.rs
      reset.rs
      store/
        mod.rs       SessionStore, UserStore, Authenticatable traits
        memory.rs    in-memory store for tests and the conformance suite
        postgres.rs  feature "postgres" (default)
        sqlite.rs    feature "sqlite"   (after Postgres is green)
        mysql.rs     feature "mysql"    (after Postgres is green)
    queries/{postgres,sqlite,mysql}/{sessions,resets}.sql   prepared query files
    migrations/{postgres,sqlite,mysql}/<timestamp>_*.sql    gavana-migrate format

All stores go through `gavana-db`, never a driver crate directly.

## Passwords

- argon2id, OWASP baseline (m = 19 MiB, t = 2, p = 1), PHC strings so params
  travel with the hash.
- Rehash on successful login when stored params are older than current.
- Hashing on `spawn_blocking`.
- Unknown email still verifies against a fixed dummy hash (constant-time
  response regardless of account existence).
- NIST 800-63B policy: min 8, max 128, no composition rules. Optional
  `BreachCheck` hook, off by default.
- `Password` newtype over `secrecy`/`zeroize`; no Debug of plaintext.

## Sessions

Opaque, database-backed. Revocable instantly; cookie carries nothing decodable.

- Token: 32 bytes from the OS CSPRNG, base64url in the cookie.
- Store `sha256(token)` only.
- Cookie `__Host-gavana_session`, HttpOnly, Secure, SameSite=Lax, Path=/.
- Idle timeout 14 days (sliding, touched at most once a minute) plus an
  absolute cap of 90 days.
- New token on every login and privilege change.
- Password change or reset deletes all other sessions for the user.
- Rows carry created_at, last_seen_at, user_agent, ip for a "your devices" UI.

Schema: see `migrations/postgres/`.

Type mapping if other backends land:

| Column     | Postgres    | SQLite               | MySQL          |
|------------|-------------|----------------------|----------------|
| token_hash | bytea       | BLOB                 | BINARY(32)     |
| user_id    | bigint      | INTEGER              | BIGINT         |
| timestamps | timestamptz | INTEGER unix seconds | DATETIME(6) UTC|
| ip         | inet        | TEXT                 | VARBINARY(16)  |

Timestamps are UTC `OffsetDateTime` above the store layer regardless of backend.

## Users table

Owned by the app. gavana scaffolding generates a `users` migration and
`queries/users.sql` into the app. Mastiff depends only on:

    pub trait Authenticatable: Send + Sync + 'static {
        type Id: Clone + Send + Sync;
        fn id(&self) -> &Self::Id;
        fn password_hash(&self) -> &str;
    }

    pub trait UserStore<U: Authenticatable> {
        async fn find_by_login(&self, email: &str) -> Result<Option<U>>;
        async fn find_by_id(&self, id: &U::Id) -> Result<Option<U>>;
        async fn set_password_hash(&self, id: &U::Id, hash: &str) -> Result<()>;
    }

## Request handling (axum)

- `MastiffLayer` (a `tower::Layer`) reads the cookie, loads session and user
  once, stores them in request extensions.
- `CurrentUser<U>`: 401, or redirect to login for HTML routes.
- `MaybeUser<U>`: `Option<U>`, never rejects.
- `Auth<U>` handle with `login`, `logout`, `logout_everywhere`.

## CSRF

Token checked on non-GET/HEAD/OPTIONS requests with a form body, or via
`X-CSRF-Token` for JS. Templates get `csrf_token()`. Bearer-token APIs exempt.

## Throttling

Sliding window: 5 failures per account per 15 min then exponential backoff;
50 per IP per 15 min. `Throttle` trait, in-memory default. Same generic error
message on every failure.

## Password reset

- Request always responds "if that email exists, we sent a link".
- 32 random bytes, stored as sha256, single use, 30 minute expiry.
- Completion sets the hash, deletes all sessions and outstanding reset tokens.
- Email goes through a `Mailer` trait until gavana's mailer crate exists.

## Configuration

    let mastiff = Mastiff::builder()
        .user_store(PgUsers::new(pool.clone()))
        .session_store(PgSessions::new(pool.clone()))
        .idle_timeout(Duration::from_days(14))
        .login_path("/login")
        .build()?;
    let app = router.layer(mastiff.layer());

## Build order

1. Harden `PasswordManager`: fix to password-hash 0.6 API, newtype,
   rehash-on-login, spawn_blocking, dummy verify.
2. Session tokens, `SessionStore` trait, in-memory store, conformance tests.
3. Postgres store over `gavana-db`'s postgres `Executor` (hand-written
   queries first if prepared codegen is not ready; swap to prepared later
   behind the same trait).
4. Axum layer and extractors.
5. Login/logout/register flows.
6. CSRF, throttling, password reset.
7. SQLite and MySQL stores, once `gavana-db` has those backends.

## Open questions (review, 2026-10-12)

1. **Multi-database.** Resolved 2026-10-16: prepared, gavana-migrate and
   gavana-db all target Postgres, SQLite and MySQL, so mastiff does too.
   Postgres ships first; the other two follow once gavana-db has them. No
   sqlx anywhere.
2. **CSRF needs to work before a session exists.** The login form is the
   classic login-CSRF target and the user has no session yet. A synchronizer
   token bound to the session cannot cover it. Use a signed double-submit
   cookie (HMAC with a server secret) for everything, which also means the
   builder needs a `secret_key`.
3. **The sessions FK hardcodes `users(id) bigint`** while `Authenticatable::Id`
   is generic. Either the sessions and resets migrations are templates the
   scaffolder writes into the app's `db/migrations/` (so the app owns the
   whole schema and can adjust the FK), or drop the FK and have the store
   delete sessions on user deletion. Templates-into-app is cleaner and also
   answers "which migration runner runs mastiff's migrations".
4. **Email normalisation.** `find_by_login` should receive trimmed, lowercased
   input, and the scaffolded users table needs a unique index on
   `lower(email)`. Otherwise case variants register twice.
5. **Per-IP throttling behind proxies** needs a trusted-proxy setting for
   `X-Forwarded-For` or everyone shares one IP. Belongs in gavana's server
   config, consumed here.
6. **Reset request rate limit.** Throttle reset requests per email and per IP
   too, or the endpoint becomes an email cannon.
7. **`__Host-` prefix in local dev.** Browsers accept Secure cookies on
   http://localhost, but not on other plain-http hosts. Provide a dev-mode
   cookie name without the prefix.
8. **Pick one time crate** (`time` vs `chrono` vs `jiff`) for the workspace
   now, since prepared's type mapping, gavana-migrate's state table, and
   mastiff all need it.
9. **Migration numbering.** The draft used `0001_`; this scaffold uses
   gavana-migrate's timestamp format.
