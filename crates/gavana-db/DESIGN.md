# gavana-db

Thin wrapper over native database drivers. gavana does not write drivers;
it gives prepared's generated code, gavana-migrate, and mastiff one small
API per backend so none of them depend on driver types directly. Decided
2026-10-16 (see `research.md` at the repo root, section 4).

## Backends and drivers

| Feature    | Driver         | Pool                      | Async |
|------------|----------------|---------------------------|-------|
| `postgres` | tokio-postgres | deadpool-postgres         | yes   |
| `sqlite`   | rusqlite       | deadpool-sqlite           | no: one worker thread per connection (tokio-rusqlite or own) |
| `mysql`    | mysql_async    | mysql_async built-in pool | yes   |

Each backend is a cargo feature. Nothing is on by default; consumers enable
what they ship. Pooling is not written here either.

## What each backend module provides

- `Executor` trait: `execute`, `query_one`, `query_opt`, `query_many`,
  `stream`. Implemented for a pooled client, a bare connection, and a
  `Transaction`, so generated functions take `impl Executor` and callers pass
  whichever they have.
- `Transaction`: wraps the driver's transaction, implements `Executor`,
  `commit` and `rollback`.
- `Encode` / `Decode`: parameter and column conversions for std types plus
  the workspace's chosen time, uuid, json, and ip types. Delegate to the
  driver's native traits; exist so generated `FromRow` impls and type
  mapping are uniform across backends.

Traits are per backend on purpose. Generated SQL already knows its dialect.
A universal `Database` trait with many associated types is the sqlx shape
and the thing this crate avoids. Cross-backend abstraction, when wanted, is
generated by prepared (one trait, one impl per backend).

## Shared

- `error`: one `Error` wrapping each driver's error with the SQLSTATE or
  equivalent, so callers match on a code, not a driver type.
- `types`: the Rust types every backend maps to. The time crate decision
  (`time` vs `jiff`) lands here and nowhere else.

## Placeholder styles (for prepared's rewrite pass)

| Backend  | Style        | Repeated param                     |
|----------|--------------|------------------------------------|
| Postgres | `$1`         | one `$1`, bound once               |
| SQLite   | `?1` or `:n` | `?1` reused, bound once            |
| MySQL    | `?`          | one `?` per use, value bound again |

## Build order

1. `postgres`: Executor, Transaction, codec for std + time types. First
   consumer is mastiff M3 and gavana-migrate phase 1.
2. `sqlite` with the worker-thread shim. First consumer is prepared's
   zero-setup query checking.
3. `mysql`.
4. Shared conformance tests: the same executor test suite runs against all
   three.

## Dependencies to add when each phase starts

tokio-postgres, deadpool-postgres; rusqlite (bundled), tokio-rusqlite or own
thread shim, deadpool-sqlite; mysql_async. Plus the chosen time crate, uuid,
serde_json, all optional behind features.
